# Phase 06 — M3U Parsing Engine

> **Epic goal:** A worker-based M3U parsing engine that turns any real-world playlist — clean or broken — into structured channel rows, streamed back in chunks with progress, at 100 k-channel scale within the < 5 s import budget.
> **Verification:** `npm test` green including all four ported m3u-utils spec files and the malformed-corpus suite; `npm run bench:m3u` shows a full worker round-trip (parse + map + chunk) of the generated 100 k fixture in < 5 s on the dev machine, with a genuine, real-browser-verified main-thread-health number recorded (not just asserted) for the 50 ms longtask bar; `npx tsc --noEmit` proves the worker protocol is exhaustively typed on both sides.
> **Status:** `shipped` · tracker: `current` — Worker, chunked protocol and the 100 k benchmark all still hold — `src/m3u/README.md` is the live reference.

Before this phase the app has a shell, platform adapters, tiered storage, and Spektrum state modules (Phases 01–05) but cannot understand a single playlist. After it, `src/m3u/` contains the ported thunder-tv utilities, the patched `iptv-playlist-parser` fork wrapped behind one module, a Vite module worker speaking the typed chunked protocol from MASTERPLAN.md §6.9, and a benchmark harness that pins the 100 k budget — everything Phase 07's import flows will drive, with no UI of its own yet.

**Chunk size correction, recorded up front (Feature 06.10.7):** the plan's own text (Feature 06.4.2, and the epic goal above as originally written) assumed `CHUNK = 5_000`. Feature 06.10's real-browser measurement (Playwright/Chromium against a real bundled `vite preview` build, not the same-thread Vitest simulation) showed 5 000-row chunks produce 50–180 ms main-thread longtasks during chunk receive — over the plan's own 50 ms budget. `CHUNK = 1_000` produced zero chunk-receive longtasks across four repeated real-browser runs. The shipped constant is `1_000`, not `5_000`; the epic goal text above and every "~20 messages" style figure elsewhere in this file has been corrected to match. Full reasoning and numbers are in `src/m3u/worker-protocol.ts`'s decision-note comment next to `CHUNK`.

## Feature 06.4 — Typed chunked worker protocol with progress events

- [x] **06.4.1** `src/m3u/worker-protocol.ts` (77 lines) defines `WorkerIn = WorkerParseIn` and `WorkerOut = WorkerProgressOut | WorkerChunkOut | WorkerSummaryOut | WorkerErrorOut`, imported by both `parser.worker.ts` and `parser-client.ts`.
- [x] **06.4.2** `export const CHUNK = 1_000` (see the "Chunk size correction" note above and the file's own decision-note comment) — **deviation from the plan's literal `5_000` suggestion, evidence-based**: Feature 06.10.5/06.10.7's real-browser measurement is what determined the final value; 5 000 produced over-budget longtasks in real Chromium, 1 000 did not.
- [x] **06.4.3** `{ type: 'progress', parsed }` emitted every `CHUNK` rows inside `handleParse`'s loop — a 100 k import now produces 100 progress messages (not ~20, per the corrected `CHUNK`), confirmed not a flood by the real per-chunk cost being sub-millisecond-to-low-single-digit-ms at this size (Feature 06.10 evidence).
- [x] **06.4.4** `{ type: 'chunk', rows, done }` slices of ≤ `CHUNK` rows, `done: true` only on the final slice — `parser.worker.ts`'s `chunkCount = Math.max(1, Math.ceil(items.length / CHUNK))` loop handles the zero-row case as exactly one `(rows: [], done: true)` chunk, tested in `parser.worker.spec.ts`.
- [x] **06.4.5** `{ type: 'summary', total, groups, radioCount, drmCount, skipped }` closes every parse — `ParseSummary` in `parser-client.ts` mirrors this shape for the promise resolution.
- [x] **06.4.6** `parser-client.ts`'s `writeChunkToStorage()` writes each arriving chunk straight to `getPlatform().storage.bulkPut('channels', records, ...)` keyed `[playlistId, index]`; a chained-promise `chunkQueue` serializes writes so overlapping `bulkPut` calls can't race and misassign indices if chunk messages arrive faster than a write resolves (a real correctness bug caught by reasoning about the design, not by a failing test — documented in the file's own comment). `parser-client.spec.ts`'s "writes each chunk with globally-increasing storage indices across multiple chunks" test (using `rowCount = CHUNK + 3` so it always spans ≥ 2 chunks regardless of the `CHUNK` value) proves no duplicate/skipped index.
- [x] **06.4.7** **Deliberately not implemented in this phase, noted as planned, not a gap**: `parser-client.ts`'s own header comment states Phase 07's real import flow owns calling `setValue('import.parsed', n)` from the `onProgress`/`onChunk` callbacks this client already exposes — inventing that Spektrum write here, ahead of a real consumer, is exactly the speculative-shape problem Phase 05 flagged for `playlist.importProgress`. The callback surface Phase 07 needs already exists (`ParserClientCallbacks`).
- [x] **06.4.8** Both switches are exhaustive: `parser.worker.ts`'s `self.onmessage` switch has a `const exhaustive: never = event.data.type` default that throws; `parser-client.ts`'s `handleMessage` switch has a `case` per `WorkerOut` variant with no default needed (all four covered) — `npx tsc --noEmit` is clean, and adding a fifth protocol variant without updating both switches was manually tried and confirmed to fail the build before being reverted.
- [x] **06.4.9** Chunk-boundary math covered by `parser.worker.spec.ts` (0 rows → one empty done chunk) and `parser-client.spec.ts` (`CHUNK + 3` rows → correct multi-chunk index continuity); `1000`/`1001`/`100000`-row exact-boundary cases are additionally exercised end-to-end by `parser.bench.ts`'s round-trip test (100 000 rows → exactly 100 chunk messages, all size `CHUNK` except the last) and `parser-perf-smoke.spec.ts` (10 000 rows).
- [x] **06.4.10** `worker-protocol.ts` has zero runtime exports besides the `CHUNK` numeric constant — every other export is a `type`/`interface`, confirmed by reading the file; `verbatimModuleSyntax` in `tsconfig.json` would itself fail the build if a type-only import were emitted as a value import, giving this a compiler-enforced guarantee, not just a visual one.
